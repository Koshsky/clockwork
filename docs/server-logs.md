# Server logs without a collector

Clockwork writes technical logs to stdout/stderr. Grafana, Loki log shipping and
OTLP are not required to diagnose a request. The existing Loki audit journal is a
separate application feature; these changes do not expire or migrate audit data.

## Find a failed request

Record the time, frontend version, backend version and the response's
`X-Request-ID`. Request IDs are generated by the backend and contain no account
or object identity. Do not include cookies, tokens or request bodies in a report.

For the managed demonstration deployment, use its existing active Compose file:

```sh
docker compose -p erp -f /opt/erp/docker-compose.yml logs \
  --since 15m --tail 1000 --no-color --no-log-prefix erp
```

To select one request from JSON logs, with `jq` installed:

```sh
request_id='paste-the-server-request-id'
docker compose -p erp -f /opt/erp/docker-compose.yml logs \
  --since 30m --no-color --no-log-prefix erp |
  jq -Rc --arg id "$request_id" 'fromjson? | select(.request_id == $id)'
```

In the root development Compose, the API service is named `backend` instead of
`erp`; the standalone frontend example uses `frontend`. Native Air logs are in
the terminal that runs the backend. For text-format logs, use a literal search
for the server-generated ID instead of JSON parsing. Do not attach `.env`,
`docker inspect` output containing environment variables or a database dump.

Each backend event includes `service=erp-backend`, its actual release version and
its component. The version is bound before migrations/repositories initialize;
local `dev` uses embedded `backend/VERSION`. It is independent of the frontend
version. Frontend/nginx, PostgreSQL and Caddy retain their own log formats; Compose
service prefixes distinguish them. This step does not pretend to turn all
third-party output into the application's safe JSON schema.

There is one `request` summary per completed API request. Operation failures or a
panic may produce an additional diagnostic event with the same ID; that is a
cause record, not a second access log. The summary has method, registered route
template, status, elapsed milliseconds and correlation IDs. Actual object paths,
queries, credentials, SQL values and user identity are omitted.

| Condition | Summary level / code |
| --- | --- |
| Successful ordinary request | INFO |
| Expected authorization/validation/conflict response | INFO with HTTP-class API error code |
| HTTP 5xx | ERROR; controlled API error code |
| Expired request context | TIMEOUT; WARN if the response is not already 5xx, otherwise ERROR |
| Cancelled request context | CANCELLED; response status remains truthful |
| Rate limit | WARN / TOO_MANY_REQUESTS; this alone is not proof of a service outage |
| Successful `/api/v1/health` probe | DEBUG, absent at the normal production INFO level |
| Panic | ERROR with no panic text/request dump; completed summary still records HTTP 500 |

Log level does not change the HTTP response, cancellation or transaction outcome.
A successful liveness probe does not prove database readiness (O13 adds a separate
readiness contract). Context expiry with a 200 response is visible as a warning;
it is not rewritten into an invented status code.

## Startup and migration failures

Bootstrap errors are JSON on stderr even when configuration cannot load. Events
carry version/component and a controlled code; migration CLI success still
writes its existing JSON result to stdout. No DSN, password, raw SQL or arbitrary
error text is printed. Use the component/event to locate the failing stage:

| Code | Operator action |
| --- | --- |
| CONFIGURATION_ERROR | Check the selected non-secret config, its readability and required variable presence; do not print their values |
| INVALID_ARGUMENTS | Use `service migrate status`, `up`, or `adopt-flyway [--dry-run]` as documented |
| DATABASE_CONNECTION_ERROR / NETWORK_ERROR | Check database reachability, container health and connection settings locally |
| MIGRATION_VALIDATION | Consult the migration/adoption guide and inspect migration status; do not force a version blindly |
| MIGRATION_EXECUTION | Inspect migration status/dirty state; schema changes may already be partially applied |
| TIMEOUT / CANCELLED | Check the failing stage and elapsed time; retry only under the operation's existing rules |

Migration checks emit start, ready or failure events with a `migration` component.
This logging does not change migrations, adoption, locking or rollback behavior.
The API emits a ready event only after its existing startup check succeeds.

## Size limits and rotation

The application accepts authored diagnostic messages up to 512 UTF-8 bytes with
no control characters. Invalid, multiline or oversized messages are replaced
with `diagnostic message omitted` and `message_rejected=true`; correlation and
error codes remain. Existing label/route bounds and the O02 field allowlist still
apply. This is a privacy/format boundary, not a promise to detect secrets in an
otherwise valid free-text message: producers must use constant messages.

All supplied Compose services, including the backend compatibility include, use
local `json-file` logging with `max-size: "10m"` and `max-file: "3"`. There is no
new agent, log network connection or change to syslog. This is approximately
30 MiB of rotated log history per container, with a possible final record and
filesystem overhead; it is not a filesystem quota. A full disk can still affect
other application data. Native terminal/file redirection needs the operator's
own rotation; Docker limits do not rotate an Air log file.

Rotation affects container stdout/stderr only. PostgreSQL, audit Loki and Caddy
volumes, business commands and backups are untouched. Do not read/truncate
Docker's internal JSON log files directly. Ordinary `docker logs`/Compose logs
remain available. Docker applies new log options to newly created/recreated
containers, not automatically to existing ones. Adopt them through the normal
reviewed deployment/recreation process; do not restart the Docker daemon or
run `down -v` to apply this configuration.

See Docker's [JSON-file rotation documentation](https://docs.docker.com/engine/logging/drivers/json-file/)
and [per-container logging configuration](https://docs.docker.com/engine/logging/configure/).
The local acceptance test emits two waves of about 50 MiB into an isolated
networkless container, verifies bounded history and stderr, then restarts it and
checks a local data marker. It does not access application volumes or build images.
