# Diagnostic data contract (O02)

Technical diagnostics are separate from business responses, stored objects and
the existing RBAC-protected audit journal. Changes here do not introduce an error
reporting service, support-bundle UI, new business queue or automatic telemetry.

## Reviewed fields

| Signal | Allowed content |
| --- | --- |
| Server logs | Constant authored event message; component/service/version/platform; server-owned request ID and trace/span IDs; registered route template; controlled HTTP method; numeric status/duration/pool counts/drop counts; critical flag |
| Server error | Closed API error code, `DATABASE_ERROR`, `TIMEOUT` or `CANCELLED`; never `error.Error()`, SQL values or connection strings |
| HTTP spans | Controlled method, registered route template or `unmatched`, numeric status, request ID; authenticated boolean, without account ID or preset name |
| SQL spans | Allowlisted operation keyword or `QUERY`, database system, numeric row count and controlled error outcome; no statement, arguments, raw DB errors or stack |
| Client diagnostic record | Closed event/error codes; bounded numeric HTTP status/duration; optional `web`/`desktop`, semantic version or `dev`, 32-character server request ID |

`internal/diagnostics` owns the server error vocabulary and secret-key recognition.
The existing logger's handler applies the attribute allowlist to direct and bound
attributes in JSON and text formats. Unreviewed fields and nested groups are
omitted; metadata cannot override built-in message/time/level fields. Log messages
are trusted authored constants, never user/error text;
`response.InternalError` deliberately ignores its legacy free-text message
argument for logging. New producers must follow that rule. Bootstrap failures
use fixed `MIGRATION_FAILED` / `INITIALIZATION_FAILED` messages.

Request IDs are generated by the server, echoed to the client and carried into
logging/tracing. The previous behavior of accepting arbitrary `X-Request-ID` is
removed so callers cannot inject secrets or personal data through correlation.
This is independent of idempotency and operation IDs, whose business behavior is
unchanged. Request IDs are not metric labels.

Gin recovery writes no request dump, raw panic or source paths; it records a
constant panic event and retains the HTTP 500 result. The request log/root span
wrap recovery so the completed request still records the error status. Technical
logs omit account IDs, IPs, idempotency keys and session IDs. Additional forensic
identity data stays in the separate business audit under its existing controls.

## Client and future support reports

`frontend/src/domain/diagnostics.ts` constructs a fresh allowlisted record. It
never serializes the supplied error/configuration/context. Axios config/body,
headers, response payloads, free-form messages/stacks, profile paths, account IDs,
server URLs, SQLite and the credential vault are excluded. Unexpected inputs use
`UNEXPECTED`; a malformed diagnostic object must not fail the business operation.
The same pure source generates Electron's `command-diagnostics.cjs` using the
existing generator. It is included in the package and unpacked-payload check.

Current network/cache/outbox/runtime console diagnostics use this constructor.
An Electron startup dialog uses a controlled error code instead of raw exception
text. No history, persistence, context buffer or diagnostic network transport is
introduced. Every record is a disposable value, so diagnostics cannot retain a
previous account's context or mutate a queued command.

O08/O09 must build history/support reports from these safe records, not attach
raw errors, application state, profile files or databases afterwards. Preview,
rotation/size limits and explicit user-triggered export belong to those stages;
O02 tests the content boundary, not a bundle feature that does not yet exist.

## Audit boundary

Audit retains authorized business content and its existing selectors, RBAC,
volumes and delivery semantics. Its JSON masker recursively recognizes sensitive
key variants regardless of case and separators, including password fields,
authorization/cookies, tokens and private keys. Malformed documents or scalar
root bodies are replaced completely: unknown content must not fail open. Ordinary
business fields are preserved. This does not sanitize arbitrary secret text
inside a business comment or retroactively clean already stored audit events.
Retention and durable audit delivery require a separate decision.

## Export policy

There is no automatic client diagnostic upload to developers or third parties.
The existing backend trace export remains governed by `tracing.enabled` (disabled
in the supplied production configuration). O02 does not silently enable or add
any telemetry destination, sampling override, public endpoint or consent flag.
Local development Jaeger is an explicit existing development configuration.

Future optional export (O04/O08/O09) must document its installation-controlled
recipient, field allowlist, sampling, limits, storage retention/deletion and how
to disable it. Credentials stay outside Git; remote export needs TLS/auth.
Unavailable receivers cannot block business requests or the Electron command
queue. No error-text matching is an acceptable replacement for an allowlist.

## Validation boundary

Canary-secret tests cover nested/case-variant audit keys and unknown bodies,
JSON/text logs including bound/grouped attributes, SQL/error spans, matched and
unmatched HTTP routes/methods, panic headers/query/body, web HTTP interceptors,
client report fields and Electron storage-error projection. Tests also check
that safe outcome codes/correlation survive, original input is unchanged, records
do not share account state and the client constructor performs no upload.
Existing application tests retain coverage of auth, RBAC, replay and offline
behavior; new diagnostic functionality is tested incrementally in later stages.
